# Shipping to mobile

| Goal | Command |
|---|---|
| Toolchain check | `gameengine doctor` |
| Device build with the debug protocol | `gameengine build android --config probe` (or `ios`) |
| Install, run, inspect | `gameengine device install`, `gameengine device run`, `gameengine device logs --follow`, `gameengine device screenshot` |
| An iPhone build with no Apple account in Xcode | `gameengine build ios --provisioning-profile <file.mobileprovision> [--bundle-id <id the profile covers>]` (or `GAMEENGINE_IOS_PROVISIONING_PROFILE`), then `gameengine device install --platform ios` and `gameengine device run --platform ios [--bundle-id <id>]` (an in-house profile gives no debug protocol session); `--unsigned` builds an app nobody signs. The profile and its certificate stay on your machine, never in the project |
| Performance on the phone (Android, dev/probe build) | `gameengine device perf [--seconds 20] [--json]`: the 20 s performance report, CPU per thread, `dumpsys meminfo` |
| All attached phones, one command (builds the probes) | `gameengine lab phones tests/lab/t2.json` (`--dry-run` to see what counts) |
| Parity + budgets on devices | `gameengine lab run tests/lab/t2.json --devices android-low-mid-mali --build android=<apk>` |
| Store build | `gameengine build android --config release --upload [--version-code n]` |
| Install a release bundle as Play delivers it | `gameengine device install build/android/<Game>-<version>-release.aab` |
| Update over the air (script, settings, content) | `gameengine release pack --version N --key release-key.json`; the game's own `name` must be in `releases.trusted` (`gameengine release keygen` prints the entry), `release apply <dir> --dir <releases dir>` tests it on desktop |
| A content release on shipped code | `gameengine release pack --version N --key content-key.json --content-of <dir>` (a release directory, or a store build's `shipped/` beside its report: keep it) |
| Publish a release | Upload the release's `files/` as it is (names change only with their bytes: skip what the CDN has), its `content-manifest-<platform>-<abi>.json` last; `--files-url https://…` when the manifest is served from elsewhere than its files |
| Cook only the bundles the CDN lacks | `gameengine cook --plan --json` lists each bundle's published name; `gameengine release pack … --only <missing names> --previous <folder of the present bundles' records>` (`<name>.json` beside each `.gpak`) |
| What a build ships (modules, cooked files, features, unused and unshipped assets, cheats) | `gameengine build android --dry-run --config release --report` (`--json` for data) |
| The cooked game boots | `gameengine check` (validate, cook, a headless smoke run of the desktop cook that fails on a data asset or streamed cell read from storage mid-frame, ADR 0089, or an asset-group member it cannot read; a `pipelines` warning), `gameengine test --cooked` |
| Pipeline warm-up for every tier | `gameengine test --tier t1 --record-pipelines` (skill `testing`) |

- Android device builds link a pinned V8 build from the engine repo's private release: run `gh auth login` and `node third_party/fetch.mjs v8` in the engine checkout once; `gameengine doctor` shows whether it is there.
- Budgets per device class live in `tests/budgets/*.json`; the lab fails on script time, GC pauses, heap, frame time.
- **Measure probe builds, not dev builds.** A dev build is a debuggable APK with Dawn validation and debug logging on; a probe build is release-optimised with the debug protocol. On a probe build on the phone: `gameengine device perf` (its `setup:` line says which profile, tier, render scale, msaa, hdr and memory class the device got), a Perfetto trace for the timeline (engine sections `frame`, `sim.step`, `script.*`, `render.*`, `present`), `gameengine device logs` for `hitch pipeline` and `memory` lines. Recipes: skill `mobile-performance-review`.
- **Release builds refuse a pipeline warm-up that is not ready**: `gameengine build android|ios --config release` stops when `pipelines.json` is missing, lacks a GPU tier (desktop, mobile, compat), names a material program no compiled material has, is older than a `*.material.ts`, or nothing can record it (no `tests/budgets/*.json` with a `structural` block and a `replay`). Re-record with `gameengine test --tier t1 --record-pipelines` and commit the file; `--allow-pipeline-issues` ships anyway (devices then compile those pipelines in play). Dev and probe builds and `gameengine check` only warn.
- Run the lab from the checkout that built the probe: its pairing key is what the device accepts.
- **Google Play's rules are checked locally (ADR 0140)**: an Android release build reads its `.aab` back and fails, with the reasons in the report's `play.problems` and `--upload` skipped, when Play would reject it: targetSdk below 36 (read from the packaged base manifest), a native library (yours, a plugin's or a vendor SDK's) not 16 KB aligned, or a base module over 500 MB per device (move content to on-demand bundles). Every upload needs a higher versionCode: pass `--version-code <build number>` (to `--stage project` on a build server). The `artifact` size budget counts the bundle without its native symbol tables, which Play keeps for crash reports and no player downloads.
- **Android API levels are the game's**: the engine builds with compileSdk 36, targetSdk 36 and AGP 8.13.2 unless `project.gameengine.json` sets `"android": { "compileSdk": 37, "targetSdk": 37, "agpVersion": "8.13.2" }` (each optional; compileSdk cannot go below the engine's). When Play announces a new minimum target, raise `android.targetSdk` (and `compileSdk` with it: a targetSdk above compileSdk fails) without waiting for an engine release. A level above the engine's tested one builds with a warning: the game owns that API's behaviour changes, so test it on a device running it. A release build below Play's minimum fails before cooking. `build-report.json` `sdk` shows each effective value and whether it came from the engine or the project.
- **32-bit Android phones are opt-in**: `"android": { "armv7": true }` in `project.gameengine.json` adds `armeabi-v7a` next to `arm64-v8a` in every build, so one release AAB serves both and Play gives each phone its own. The 32-bit player runs Hermes, not V8 (as iOS does), so keep game tests green with `gameengine test --js both`; the first such build compiles Hermes for Android once (CMake and Ninja). `localeCompare` and locale-aware upper/lower case are locale-free there.
- Releases carry no machine code: Rust systems (`native/`) ship in a store build and keep running from the binary, and transpiled systems run their TypeScript when a release changed them. Only the game's own app applies a release of a game with `native/` (`E_NATIVE`). A store update retires installed releases.
- **Your game's own updates need no code:** set `releases.manifest.url` and list the game's id in `releases.trusted`; after start and on return to the foreground the engine checks the manifest for this app's release channel, downloads what it offers and applies it (live when only content changed, else at the next start), and logs `self-update: …`. `{channel}` is the app's channel, any name you choose (`inhouse`, `store`, `beta`, a branch): `releases.channel` in `project.gameengine.json`, or `gameengine build --channel <name>` for one build (`releases.status` reports it), so testers or a branch get a release before players do: publish each channel's manifest at its own URL, e.g. `https://cdn/…/{id}/{channel}/content-manifest-{platform}-{abi}.json`. A missing manifest (404, or 403 from a bucket that does not list) means nothing is published yet. A release staged for the next start is not fetched again; loose desktop runs and web players skip the engine's update. `release pack --channel <name>` picks the channel its files and manifest are for (unset: `releases.channel`); an unknown `{…}` in the URL fails the config. `{buildType}`, `--build-type` and a project with no `releases.channel` (the bundle id then decides: `inhouse` for `.inhouse`, else `store`) still work but warn `W_DEPRECATED_BUILD_TYPE`, and `gameengine check` reports it: do what the warning says.
- **From the game (`services.releases`, UI code only):** `check({ manifest? })` checks the game's content manifest, passed in (fetched by the game) or from `releases.manifest.url`, for a release this device can apply (`{ latest, available?: { version, live, bytes } }`; sends `available` once per version); `download({ id })` fetches the files of the release it offers that the device lacks (or any release directory by `url`) and keeps it; `apply()` applies your own update (live when only content changed, else at the next start, `now: true` for a new session behind a cover). `status({ id })` says what the device keeps. Launching other games is `services.launcher` (below).
- **The content manifest:** `release pack` writes `files/content-manifest-<platform>-<abi>.json`: one release, its files by published name, size and SHA-256, signed with the release or the content key. A device refuses one older than the one it keeps. `releases.manifest` in `project.gameengine.json`: `url` (a template with `{id}`, `{channel}`, `{platform}` and `{abi}`) and `refresh` (`onStart`, `onForeground`, `minIntervalSec`, default 900; `retrySec`, default 60, after a failed fetch); without it, fetch the manifest yourself (e.g. from your studio's asset service) and pass its text to `check({ manifest })`. `releases.feed` and `release publish` are gone (ADR 0122 amendment 2026-10-13). Two keys per game: the **release key** (`releases.trusted[].publicKey`) signs code; the **content key** (`contentKey`, the content team's, never the same key) signs releases that keep a code the device already trusts, so it cannot ship code (content bundles holding scripts or settings are refused). Keep both out of the repo (`docs/ota-policy.md`).
- **Publishing rules:** the version only grows (use the build number); a content release reaches only devices already on its code, so release code changes with the release key and make content releases `--content-of` the release that shipped that code (or the store build's `shipped/`). One `releases.check` per game runs at a time: calls meanwhile share its answer.
- **A hub (an app that launches other games, ADR 0121):** list each game in `releases.trusted` with its public key, or one studio key as `{ "id": "*", "publicKey": … }` that signs every game the hub launches (the hub then finds its games at runtime in a list of its own, ADR 0122 amendment; a studio key never turns the hub's own updates on), and point `releases.manifest.url` at the games' content manifests (`{id}` is the game's id, `{channel}` the game's channel: `releases.channels`, else the app's) or pass each game's manifest to `check({ id, manifest })`; on Play, `releases.check({ id, force: true })`, `releases.download({ id })` when it offers one, then `services.launcher.launch({ id, data })` (`data`: optional JSON of at most 64 KB the hub defines, e.g. `{ level: 7 }`, which the game reads with `services.launcher.status()` → `{ launched, by, data }` and starts from: the hub then owns which level a game plays); a kept copy launches when nothing is newer or the check or a download fails. A game's own project lists its key in `releases.trusted`, which also gives that game's own app a release store. After that frame the hub's session waits, suspended, under the game's (its state, views and memory stay; save anyway, a phone may end the app). The game ends with `services.launcher.exit({ result })` (64 KB of JSON at most); the hub resumes where it was and gets `services.launcher.on('exited', ({ id, result, reason }) => …)` (`reason`: `exit`, `error` or `quit`). Nothing reboots the hub any more, so its `exited` handler clears what it set up to launch (a busy flag, a cover, a status line). Its own downloads and sockets keep going while the game runs and report when it runs again. `launcher.status()` tells a game whether a hub launched it. **Asking the hub mid-level:** the game calls `services.launcher.ask({ message })` with JSON the hub defines (e.g. `{ type: 'booster', booster: 'hint' }`); the game pauses after that frame, the hub runs over its last frame with `launcher.on('asked', ({ ask, id, message }) => …)` and answers with `services.launcher.answer({ ask, reply })`, and the game's `ask` resolves with `{ reply }`. Turn a reply into sim input with `emit` (never act on it in the sim directly); one question at a time (`E_BUSY`); the hub launches nothing while one is open. Game tests mock the hub with `ctx.services.mock('launcher.ask', { result: { reply } })`; hub tests play a question with `ctx.services.emit('launcher', 'asked', { ask, id, message })`. A launched game cannot download, apply or launch, and `net.downloadFile` writes only into its own data folder; its `app.quit()` hands back to the hub, on iOS too. To show a result screen over the game that just ended, draw `<Sprite src={RELEASES_LAST_FRAME} />` (from `@gameengine/runtime`, sized explicitly, e.g. to fill the screen): the frame the game handed back on, kept until the next launch, an app update applied now or a lost GPU device; before any hand back it draws nothing. `releases.launchFadeMs` (0–5000, default 0) fades the hub's last frame out over the game's first frames instead of cutting. Finish purchases and ads before `launcher.exit` (and a hub before `launcher.answer`): a store event that arrives after the switch reaches the hub. It works on phones, in the desktop player, in the editor's Play (hot reload waits until the game hands back) and in `gameengine run --headless`. On a phone the manifest and its files are served over https (iOS lets plain http reach only the device itself, `127.0.0.1`, which the iOS simulator shares with the Mac; Android's shell allows none) and the release is packed for that platform (`release pack --platform ios|android`). A release build of a hub stops with `E_POLICY` until the App Store and Play review in `docs/ota-policy.md` is done; then build with `--store-policy-reviewed`. Samples `game-hub` and `hub-test-game` in the engine repo.
- **One game from another channel in a hub:** `releases.channels` maps a game id to its channel (`{ "ColorSearch": "feat-hint-booster" }`), or `gameengine build --channel-for <id>=<name>` sets it for one build. That game's manifest URL, signed channel and `release fetch --channel-for` use it; every other game and the hub's own updates stay on `releases.channel`. A code release of the hub replaces its shipped config, map included: pack it with the same `--channel-for` as the build its devices run (`release pack --channel-for`), or those games go back to the hub's channel after the update. A content release (`--content-of`) keeps the map.
- Engine library size: `--report` prints `libgameengine (arm64-v8a): N MB linked and stripped, as the APK carries it` — the static library cargo builds (~300 MB: all of V8, debug info) is linked with unreached code dropped and stripped by the Android build (~41 MB for arm64 at V8 + the engine). The shell hides the static library's symbols, so the linker drops what the `gameengine_*` entry points never reach; `--report --json` has the number as `libs.<abi>.libgameengineLinked` (null without an NDK clang). Compare that number, not the static library, with an APK budget; it needs the NDK, and a `--dry-run` measures the library the last real build left (dev and probe ones carry the debug protocol).
- Device builds ship minified code with `DEV` false: put debug-only presentation code (overlays, extra logs) under `if (DEV)` with `import { DEV } from '@gameengine/runtime'` and it is removed. Never let sim state depend on `DEV`.
- Cheats (`src/**/*.cheats.ts`, skill `cheats`) ship in dev and probe builds and are left out of release builds unless you pass `--cheats` or set `"cheats": { "release": true }`; `--report` says `cheats: included`. Nothing may import a `*.cheats.ts` file: a release build that reaches one fails.
- Low-end phones have their overrides (skill `device-tiers`): `gameengine validate` is clean and
  a T1 run at `--memory-class phone-low` passes; measure a probe build on a `phone-low` phone
  (about 3 GB RAM, Mali-G52-class GPU) before shipping.
- Phones run at most 60 fps whatever the display (ADR 0079), and the `compat` tier and `phone-low` phones (3 GB RAM or less) 30 unless the project sets `render.targetFps.compat` / `render.targetFps["phone-low"]` (ADR 0102; a deliberate per-project choice, measured on such a phone); lower it per screen with `quality.setTargetFps(30)` (skill `mobile-performance-review`).
- `validate` (and so `check` and every build) fails with `E_PLUGIN` when code uses a service no enabled plugin implements; `haptics`, `keyboard` and `net` are built in; `push`, `system`, `cloudsave` and project services need their plugin in `plugins` (skill `platform-services`).
- Cooked builds ship scenes only from `scenes/` and prefabs only from `prefabs/`; the engine refuses other document paths in dev too, and `gameengine check` boots the cooked game before you build. Dev and probe builds draw the latest error as a red banner over the game (release builds only log it): a device stuck on a loading cover shows why.
- Never import `@gameengine/test`, the engine's `examples/services/*` (copy those into the project) or anything from `tests/`, `tools/`, `editor/` or `playable-ads/` in game code: the cook fails. Built-in packages a game switches on (`project.gameengine.json` `packages`) and npm packages ship their code, never their `editor/`, `tools/`, `dev/` or `tests/`.
- `project.gameengine.json`, `input.json`, `pipelines.json` and `services.gen.json` ship to the device as they are: never put secrets there (SDK keys are `"env:NAME"`; store builds drop `services.mocks`). Only files a bundle's `include` matches ship (samples use `"**"`): the cook warns about the rest, and `--report` lists them as "files no bundle includes" next to files nothing names. A bundle's `exclude` globs keep files out on purpose (source art kept for baking): no warning, listed as "files bundles exclude". Smaller textures: `compression = "astc6x6"` in a texture's `.gmeta` (skill `asset-memory`); sounds: skill `audio` (its pre-ship checklist).

## App icons and launch screen (`branding`)

`branding` in `project.gameengine.json` (editor: Build ▸ App Icons & Launch Screen…):

```json
"branding": {
  "icons": { "active": "default", "sets": {
    "default": { "source": "branding/icon.png",
                 "ios": { "dark": "branding/icon-dark.png" },
                 "android": { "foreground": "branding/icon-fg.png", "background": "#1a0f2e" } } } },
  "launch": { "image": "branding/launch.png", "background": "#1a0f2e", "fit": "cover" }
}
```

- `source`: square PNG ≥ 1024 px, full bleed, no transparency (iOS flattens it onto black). Android `foreground`: ≥ 432 px on transparency, art inside the centred 66/108.
- Set ids are lower case (`[a-z][a-z0-9_]*`); non-active sets ship as alternate icons.
- `gameengine build <platform> --dry-run --json` checks the images (errors stop the build) and writes the files; look at `storeIcons` in the report and `<project>/.gameengine/build/<platform>/<config>/store/` for the listing icons.
- iOS keeps the launch screen up until the game's first frame is on screen, and that frame waits (at most 2 s) until the first screen's art and glyphs have loaded, so a cold start goes from the launch screen straight to a complete screen. Show `launch.image` in that first screen (a boot view, `loading.boot`) and the hand-off is seamless.
- Android 12+ splash is a centred icon on `launch.background`; the full `launch.image` is the engine's first frame, drawn as it loads. The file ships to devices: paths only, never secrets.
